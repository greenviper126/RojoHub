# Upstream

Rojo-Hub's Studio plugin is Rojo's Studio plugin with a few hooks added, so that Rojo-Hub can
connect it by itself (spec 007) and keep it connected through switches and restarts (spec 010).
Rojo's code is kept **unedited** and Rojo-Hub's changes ride on top of it, so moving to a new Rojo
release is one command.

## Layout

- `upstream/` is Rojo's `plugin/` folder at the tag in `upstream.json` (now `v7.7.1`, commit
  `26b6cc6`), exactly as released: `src`, `fmt`, `http`, `log`, `rbx_dom_lua`, `Version.txt`, and
  each package in `Packages/` at the submodule commit upstream pins (only its licence,
  `default.project.json` and the folder that builds; TestEZ is left out, upstream uses it only in
  dev builds). `LICENSE.txt` is Rojo's licence from the repository root. `upstream.json` records the
  tag, commits and a hash of every file; a unit test fails on any edit.
- `patches/` holds Rojo-Hub's changes to Rojo's files, one patch per file. Each is a few lines,
  marked `-- Rojo-Hub`, that call into `RojoHub/`.
- `RojoHub/` is Rojo-Hub's own code (MIT, like the rest of this repository; it says so at the top).
  It is staged as `src/RojoHub/`.
- `default.project.json` is upstream's `plugin.project.json` with paths relative to the staged
  folder, `*.spec.lua` left out of the build, and the Creator Store upload details dropped.
- `rbx_dom_lua.LICENSE.txt` is rbx-dom's licence (MIT), staged as `rbx_dom_lua/LICENSE.txt`:
  upstream copies rbx_dom_lua from rbx-dom without it.
- `selene.toml` and `testez.yml` (Rojo's, for selene's `roblox+testez` std) lint the staged folder.

`node tools/plugin.mjs stage` (run by `npm run build`) copies `upstream/`, applies `patches/`, and
adds `RojoHub/` and the files above into `dist/plugin-src/`, which Rojo 7.7.1 builds into
`dist/RojoHub.rbxm`.

## Licences

MPL-2.0 (`upstream/LICENSE.txt`) covers every file from Rojo, and the patches to them. Each package
keeps its own licence in its folder. Everything is credited in the repository's
`THIRD-PARTY-NOTICES.md`, generated by `tools/notices.mjs` from `upstream.json`.

## The patches

- `src/App/init.lua`
  - requires `Plugin.RojoHub`;
  - in `App:init` (edit mode), starts the Rojo-Hub link instead of calling `tryAutoReconnect` at once,
    and hands `tryAutoReconnect` + `checkSyncReminder` to it as the fallback when the service does
    not answer;
  - `App:setHubMatch` (new) keeps the service's answer in `state.hubMatch`;
  - `App:checkSyncReminder` returns early while the service answers (the saved address may be stale);
  - `App:willUnmount` stops the link;
  - `App:endSession` and the Confirming page's `onAbort` tell the link the user ended or declined
    that session, so it is not reconnected by itself; `App:endSession` with no session ends a held
    loss (spec 010);
  - `pluginName` is `"Rojo-Hub"` rather than `"Rojo " .. version`: Studio refuses a second dock
    widget with the same id, so the two plugins could not both load;
  - the NotConnected page gets `hubEnabled`, `hubMatch` and `onHubConnect` (the *Connect to
    <project>* button);
  - `App:startSession` takes an optional `{ host, port }` to connect to instead of the address boxes,
    and saves the boxes' values (not that address) as the place's last address, so Rojo-Hub never
    writes the boxes;
  - the confirm callback accepts, before Rojo's own rules, a patch for a project this place has
    synced with before (`hub:accepted`, from the service), unless *Confirmation Behavior* is *Always*;
  - spec 010: the session's *Disconnected* status asks `hub:holdLoss` first and shows nothing while
    the link waits for the restarted project; *Connecting* and *Connected* show no page change or
    notification while it resumes (`hub:isResuming`).
- `src/App/StatusPages/NotConnected.lua`: renders `RojoHub.ConnectButton` (only while the service
  answers *connect*) and `RojoHub.StatusLine` under the buttons.
- `src/App/StatusPages/Connected.lua`: the changes viewer follows the current session, since a
  quietly resumed restart keeps the page (spec 010).
- `src/App/StatusPages/Settings/init.lua`: a *Rojo-Hub Auto Connect* row (`hubAutoConnect`).
- `src/Reconciler/reify.lua`: creates instances through `RojoHub.Adopt`, which adopts an existing
  instance where one cannot be created (`StarterCharacterScripts` added by a switch), and leaves an
  adopted instance's `Name` and `Parent` alone (spec 010).
- `src/Settings.lua`: `hubAutoConnect = true`; `checkForUpdates` defaults to `false`, since Rojo's update
  check points at Rojo's own plugin and this one updates with Rojo-Hub.
- `src/Version.lua`: `isApiBlocked` (new in 7.7.1, called when the settings page draws) asks
  api.github.com only while update checks are on, so Studio does not prompt for that domain.

## Changing a patch

1. `node tools/plugin.mjs stage` (into `dist/plugin-src/`).
2. Edit the staged files. Keep changes to Rojo's files to small hooks marked `-- Rojo-Hub`; put the
   rest in `src/RojoHub/`.
3. `node tools/plugin.mjs save` rewrites `patches/` from the stage and copies `src/RojoHub/` back.
4. List the change above.

## Moving to a new Rojo release

1. `node tools/plugin.mjs update v7.x.y`. It fetches the tag and its submodules, carries each patch
   over with a three-way merge, rewrites `upstream.json`, and replaces `upstream/` only if every
   patch merged. On a conflict it leaves `patches/<file>.patch.merged` (the whole merged file with
   conflict markers) and changes nothing else: resolve it, put it in a stage, `save`, and run
   `update` again.
2. Check `protocolVersion` in `upstream/src/Config.lua`: a new protocol means the service must refuse
   projects pinning older rojo (spec 007).
3. Bump `PLUGIN_ROJO` in `build.mjs` and the Rojo versions installed by `.github/workflows/`, run
   `node tools/notices.mjs`, build, and try it in Studio.
