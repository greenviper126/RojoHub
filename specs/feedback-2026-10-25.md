## Two projects listing the same place

Seen live: VluxyBuildingTools and FolderThemes both list the same place in `servePlaceIds`. The
place kept to VluxyBuildingTools (the project it last synced with), and FolderThemes showed
`connections: 0`. The only fix was assigning the place in the panel.

What the service already does (`src/service/studio.ts`, `matchPlace`):
- An assignment made in the panel wins and is kept across reconnects and restarts (`PlaceMemory`).
- When several projects claim a place, it stays with the project it last synced with. With no such
  project and several serving, it asks for a choice (`status: "choose"`).

What is missing:
1. Agents can't see the conflict. `status` and `serve_here` don't say that another project also
   claims the place, or which project currently holds it. The agent only sees `connections: 0`.
2. Agents can't hand a place over. The MCP instructions say "You cannot choose which project a
   Studio place syncs with". The proposal is a tool to reassign a place, refused unless the user
   approves or yolo is on, the same as stopping a synced project.
3. Nothing warns about a shared `servePlaceIds` entry. The panel only shows "choose" when no
   project wins. It doesn't flag a place that two projects list but that one of them holds quietly.
4. Deferred: syncing two projects into one place at once when their trees don't overlap. This
   breaks the one-owner rule, so it needs its own spec.

Outcome: built as spec 014 (0.22.2). Syncing two at once is a non-goal for good.

## Field test of 0.22.3

The test passed:
- Iso Dev's plugin went from 0.22.1 to 0.22.3 on reopen.
- The FolderThemes / VluxyBuildingTools request and move worked live.
- TheLaundryShift recovered by itself after its served worktree was deleted.

Observations:

1. Agent chats opened before a service update keep the old tool list. A chat whose launcher
   started 27 s before 0.22.3 replaced the old service had no `version` tool. Still to check:
   whether Claude Code acts on the launcher's `tools/list_changed`, or whether every open chat needs
   `/mcp` reconnect after an update. The answer goes in the release notes either way.
2. "Already open" when the place is not usable yet. `PlaceOpener.openNow` (`src/service/places.ts`)
   counts a place as open when a plugin reported it, or when a Studio process's command line names
   it. The service log shows the old 0.22.1 Iso Dev window said hello at 22:19:26, and the
   successful open was at 22:27:44, so the first `ensure` most likely saw the old window while it
   was closing. This is a race, not a stuck state.
   - Proposal: say which evidence was used, e.g. "a Studio process for it is running but its plugin
     has not connected". When only a process is seen and no plugin says hello within a grace
     period, `ensure` should open it again instead of waiting forever.
3. Agents check out branches in a folder Rojo-Hub serves. Other sessions keep switching
   VluxyBuildingTools' served checkout, so Studio gets whatever branch is checked out. This also
   risks rojo-rbx/rojo#1305: a checkout that removes a folder the running rojo watches can panic
   rojo. Rojo-Hub cannot refuse a `git checkout` it doesn't run (a git hook would be invasive).
   - Proposal: a stronger line in the MCP instructions ("never check out another branch in a
     folder Rojo-Hub serves; use new_branch").
   - Proposal: `status` and `serve_here` say it outright when the served folder's branch changed
     under the hub, naming `new_branch`.
4. Duplicate group: "TheLaundryShift 2" (id `thelaundryshift-2`) has the same three projects as
   "TheLaundryShift". Group names are unique and no feature copies groups, so someone created it by
   hand or with `create_group`. It is not a bug.
   - Optional: `create_group` warns when a new group has exactly the members of an existing one.
   - The duplicate itself is the user's to delete.
5. Wanted: when a project's served worktree is deleted, switch it back to the repo's main checkout.
   Correction from the Opus review: no code does this. TheLaundryShift's rojo crashed at 00:49
   (rojo.previous.log). The restart failed because the folder was gone, and the project stayed in
   error until something (an agent or the panel) switched it to main at 17:22.

Plan (Opus review), ranked. Built in 0.22.4: items 2 and 3 in full, and item 4's wording and logs (the
evidence, the disconnect log). Held back as behaviour changes, awaiting the user: item 1 (fall back to
the main checkout), item 4's `ensure` re-open retry, and item 5 (no change anyway).

1. Fall back to the main checkout (or the claim's `returnTo`) in `startLocked` when the served
   worktree is gone. Add a note, log it, and drop the dead claim.
2. Launcher: the service sends `x-rojo-hub-version` on `/mcp`. The launcher compares it on every
   answer and sends `tools/list_changed` when it changes. Today it notices a new service only if a
   call fails.
3. Checkouts in a served folder: stronger MCP instructions. Keep the checkout note through a
   same-target switch (`switchLocked` clears it now). `serve_here` from the main checkout says to
   use `new_branch`. Serving a per-commit view of main instead is out of scope.
4. "Already open": say the evidence (plugin, or a Studio process with its pid). Log plugin
   disconnects. `ensure` opens again once, but only after the Studio process naming the place has
   exited. No timed retry, which would risk a second copy.
5. Duplicate group warning: no change for now.
